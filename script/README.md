# Custom Server operations

The custom app lives at `~/Applications/BlueBubbles-Custom.app`; the shared `/Applications/BlueBubbles.app` may belong to another logged-in user.

- `./script/build_and_run.sh --verify` runs custom regressions, rebuilds UI/server, packages, snapshots the previous app and database, installs, launches and reports health. It keeps the existing app running until packaging succeeds. Dependencies must first be installed using the project Node 20 toolchain and `electron-builder install-app-deps` from `packages/server`.
- `./script/build_and_run.sh --build-only` prepares a package. `--install-only` installs that validated package without repeating the build. `--logs`, `--telemetry` and `--debug` support investigation.
- `./script/health.py --strict` compares seven days of source message/reaction GUIDs with a checked bridge snapshot, reports HTTP/helper/bridge health and returns nonzero on gaps or unavailable helpers. `--days N` chooses 1–90 days. It prints no credentials, handles, GUIDs or message content. One persistent bridge socket is normal while idle; a second HTTP connection appears during queries.
- `./script/diagnose_findmy.py` reports whether the current user's Find My requires library validation and has mapped the custom library. A connected helper with zero friends differs from a library that never connected. POST refresh now reports the latter as an error; GET cached data remains available.
- `./script/install_startup.py`, invoked while the Server is stopped, installs `com.bluebubbles.server` for user login and `local.bluebubbles.custom-health` for a five-minute report. The launcher opens the custom app only if absent, waits for HTTP readiness, then restarts only `com.beeper.bbctl.sh-imessage` for catch-up. The app's `launch-agent` setting corresponds to that service.

Local packages include `custom-build.json` identifying source commit and server hash. Official release checks remain available, but these marked packages cannot automatically replace themselves with an official build. Update through this build workflow to preserve local fixes.

Find My on this installation has library validation enabled and does not map the injected dylib. A controlled launch with a nonexistent injected-library path leaves Find My running while an unprotected control aborts on that same path. Find My honors loader print diagnostics but ignores the insertion request. An ad hoc signed, user-local copy is rejected by taskgated as an invalid signature, so re-signing a copy is not a working alternative.

The Server's requirements panel now accepts only the explicit `SIP ... disabled` status; `unknown (Custom Configuration)` does not establish that requirement. On macOS 15+ with Find My startup enabled it also reports the documented Library Validation preference separately. These are diagnostics and do not gate or stop an existing Messages helper. A missing preference fails the check; a preference being present alone does not prove that injection succeeds. Verify actual mapping, registration, and Friends/Devices refreshes with the probe.

The official [Private API setup guide](https://docs.bluebubbles.app/private-api/installation) describes a system-wide Library Validation change. Do not apply it automatically during build or startup. On a shared Mac, obtain approval before applying it; record the previous value and restore that state if the controlled test does not help. No system application, code-signing protection, SIP configuration or other macOS user's process is changed by these scripts.

This Mac uses OCLP 2.5.1, AMFIPass 1.4.1, and the normal OCLP root-patching SIP mask `0x803`. That partial configuration is not itself an OCLP fault. [AMFIPass supports root patches with AMFI and Library Validation enabled](https://github.com/dortania/OpenCore-Legacy-Patcher/releases/tag/0.6.8); working root patches do not prove that arbitrary helper injection is permitted. The documented preference was absent before the controlled test below. Neither that absence nor the OCLP SIP mask alone establishes which policy change is needed; do not infer that broader SIP or EFI changes are necessary.

On November 12, 2026, an approved controlled test set `DisableLibraryValidation` to true, relaunched only the custom Server's Find My child, and verified the preference while testing. The helper still did not map or register, and Friends/Devices refreshes both returned HTTP 500. The timed guard restored the previous absent preference file, then Find My was relaunched again. The Server and Beeper connection remained running and the four attachment exceptions retained the same GUID-set fingerprint. This was a process-relaunch test; it did not include a reboot or a system-daemon restart.

Local OCLP installation logs show a September 16, 2026 build with AMFI explicitly disabled and CSLVFixup included, successfully transferred to the EFI partition. The current boot lacks that AMFI-disable argument and CSLVFixup. This supports a historical configuration difference without establishing the exact replacement date, whether that earlier build was booted, or whether the separate preference ever existed. OCLP's relevant security/default/detection code and AMFIPass payload did not change between 2.4.1 and 2.5.1.
